## Проект: Animal Ball Shooter FPS

Браузерный 3D шутер от первого лица. Игрок стреляет шариками, персонажи — животные. Игра работает полностью в браузере без установки.

## Технологический стек

- **Three.js** — 3D рендеринг (WebGL-обёртка, огромная экосистема, лучший выбор для браузерных FPS)
- **Vite** — сборщик (быстрый HMR, нативный ES-модули)
- **Cannon-es** — физический движок (форк Cannon.js с поддержкой ES-модулей)
- **SkeletonUtils** (`three/addons/utils/SkeletonUtils.js`) — клонирование skinned mesh с анимациями
- Чистый JS (без фреймворков) — игровая логика

## Команды разработки

```bash
npm install          # установить зависимости
npm run dev          # запустить dev-сервер (http://localhost:5173)
npm run build        # собрать продакшн в ./dist
npm run preview      # превью продакшн-сборки
```

**Важно:** открывать игру только через `http://localhost:5173`, не через `file://` — иначе CORS блокирует скрипты.

## Архитектура игры

**Игровой цикл** (`main.js`): `requestAnimationFrame` → `world.step()` → `player.update()` → `shooter.update()` → `spawner.update()` → `renderer.render()`. При `alive = false` физика и логика останавливаются, рендер продолжается.

**Физика**: каждый объект имеет `THREE.Mesh/Group` (визуал) + `CANNON.Body` (физика). После каждого `world.step` меш синхронизируется с телом вручную в `update()`.

**Камера**: PointerLock через `renderer.domElement.requestPointerLock()`. Мышь обрабатывается в `Player.js` через `mousemove`. Камера сдвигается вверх от центра тела (`body.position.y + 1.2`).

**Шарики** (`BallShooter.js`): при выстреле — `THREE.Mesh` + `CANNON.Sphere` с импульсом в направлении камеры. Коллизия через `body.addEventListener('collide')`. Шарики живут 4 сек или до попадания. Материалы — один экземпляр на все шарики (`ballMat.clone()` для каждого).

**Враги** (`Enemy.js`):
- Клонируются через `skeletonClone(gltf.scene)` — обязательно для skinned mesh, иначе анимации ломаются
- Каждый враг получает `child.material = child.material.clone()` — иначе вспышка при попадании срабатывает на всех
- Root motion убирается фильтрацией треков с `.position` на костях `hips`/`root` перед `clipAction`
- При контакте с игроком (dist < 1.2) наносят 10 HP раз в секунду (`_damageCooldown`)
- Смерть: физ. тело удаляется сразу, меш уменьшается за 0.4 сек, затем удаляется из сцены

**Система HP** (`main.js`): `MAX_HP = 100`, при 0 → `onDeath()` → `exitPointerLock()` → экран смерти. Рестарт через `location.reload()`.

**Коллизии шарик→враг**: `Map<CANNON.Body, Enemy>` (`enemyBodyMap`), передаётся в `BallShooter` и `EnemySpawner`. Враг добавляет своё тело в map при создании, удаляет при смерти.

**Уровень** (`Level.js`): загружает `level.glb`, смещает на `LEVEL_OFFSET = (-5, 0, 5)` чтобы центровать стартовую комнату вокруг начала координат. Физика стен строится автоматически — для каждого меша уровня берётся bounding box и создаётся `CANNON.Box(mass=0)`. Работает потому что уровень состоит исключительно из box-примитивов.

**Координатное преобразование Blender → Three.js** (export +Y Up):
- Blender X → Three.js X
- Blender Y → Three.js −Z
- Blender Z → Three.js Y

Стартовая комната в Blender (X:0–10, Y:0–10) становится в Three.js (X:0–10, Z:0–−10). После LEVEL_OFFSET центр комнаты — (0, 0, 0). Игрок спавнится в (0, 1.5, 0).

## Workflow с Blender → игра

1. Моделировать персонажа, применить `Ctrl+A → All Transforms`
2. Риговать через Mixamo (загрузить OBJ/FBX, скачать с анимацией как FBX)
3. Импортировать FBX в Blender (`Automatic Bone Orientation`), переименовать анимацию в Action Editor
4. Экспортировать: `File → Export → glTF 2.0 (.glb)`, включить Animations, +Y Up
5. Положить в `public/assets/models/animals/`
6. Добавить в `AssetLoader.js`, передать в `EnemySpawner`

**Известные проблемы Mixamo:**
- Root motion на `mixamorigHips.position` → решение: фильтровать треки в Enemy.js (уже реализовано)
- Шкала: если персонаж огромный — поменять `MODEL_SCALE` в `Enemy.js` (сейчас `1.0`)

## Правила работы (обязательно соблюдать)

### Думать перед кодом
- Явно формулировать допущения. При неопределённости — спрашивать, а не угадывать.
- Если возможны несколько подходов — называть их, не выбирать молча.
- Если что-то непонятно — остановиться и спросить, не додумывать.

### Простота прежде всего
- Минимум кода, решающего задачу. Никакой спекулятивной функциональности.
- Нет абстракций для единственного применения.
- Нет «гибкости» или «конфигурируемости» без запроса.
- Если решение занимает 200 строк, а могло 50 — переписать.

### Хирургические изменения
- Трогать только то, что нужно для задачи.
- Не «улучшать» соседний код, комментарии или форматирование.
- Совпадать с существующим стилем кода.
- Заметил мёртвый код — упомянуть, не удалять.

### Выполнение по целям
Для многошаговых задач сначала озвучить план:
```
1. [Шаг] → проверка: [что проверить]
2. [Шаг] → проверка: [что проверить]
```
Трансформировать задачи в проверяемые цели перед реализацией.

### Контекст художника
Пользователь — художник с навыками 3D в Blender. Технические объяснения давать кратко; больше внимания уделять тому, *как* художественные ресурсы интегрируются в код (форматы, настройки экспорта, pipeline). При выборе подходов предпочитать те, что дают художнику больше контроля над визуалом.
